# Хостинг: переезд с Vercel на свой сервер

## Зачем

База с персональными данными переехала в РФ 30.07.2026, и 242-ФЗ (ст. 18.5)
этим закрыт. Но функции `api/` обрабатывали те же данные — телефоны, имена,
переписку, платежи — на серверах американской компании. Это **трансграничная
передача** по ст. 12 152-ФЗ: она требует отдельного уведомления РКН до начала
передачи, а США не входят в список стран с адекватной защитой прав субъектов.
Плюс сугубо практическое: Vercel уже ограничивал российские аккаунты и оплату.

После переезда вся обработка ПДн происходит на одном сервере в Москве.
Зарубежными в цепочке остаются только внешние сервисы, о которых пользователь
предупреждён отдельно: Telegram (бот репетитора) и DeepSeek (генерация ДЗ).
GitHub остаётся местом хранения кода и сборки статики — персональных данных там
нет, к ст. 12 это отношения не имеет.

## Что где лежит

Всё живёт на том же сервере, что и база (`ssh precettore-db`, Timeweb MSK-1).

| Что | Где |
|---|---|
| Статика (`dist/`) | `/opt/precettore-web/current/dist`, отдаёт Caddy |
| Функции `api/` | контейнер `precettore-web`, порт 8787 только внутри сети |
| Секреты | `/opt/precettore-web/api.env` (root, 600), деплой их не трогает |
| Конфиг сайта | `/opt/precettore-db/volumes/proxy/caddy/precettore.caddy` |
| Описание контейнера | `/opt/precettore-db/docker-compose.web.yml` |

Исходники этих файлов — в репозитории: [`server/`](../server). На сервер они
попадают копированием, автоматической синхронизации нет: правку конфига надо
осознанно повторить на сервере (`scp` + `caddy reload`).

Наружу порт 8787 не публикуется вовсе. Это принципиально: docker вставляет свои
правила в iptables **до** ufw, поэтому «опубликовал на 0.0.0.0» на этом сервере
означает «открыл в интернет» несмотря на `ufw default deny`.

## Как устроен запуск функций

Обработчики в `api/` **не переписывались**. У Vercel контракт функции — обычные
node-шные `IncomingMessage`/`ServerResponse` плюс немного сахара (`req.body`,
`req.query`, `res.status().json()`). [`server/index.js`](../server/index.js)
досыпает ровно этот сахар и зовёт тот же `export default`. Поэтому один и тот же
код работает и на Vercel, и у нас, а откат — это переключение DNS, а не откат
кода.

Адреса заданы явной таблицей, а не сборкой пути из URL: путь из запроса,
подставленный в `import`, — это обход каталогов.

`/api/healthz` и `/healthz` отвечают `{ok, routes, ip}`. Поле `ip` — тот адрес,
который сервер видит у клиента; см. следующий раздел.

## Адрес клиента — самое хрупкое место переезда

На адресе клиента держатся ограничитель частоты и первая ступень проверки
вебхука ЮKassa. При переносе «как есть» здесь была бы дыра: раньше
`clientIp()` брал **первый** элемент `x-forwarded-for`, а Caddy дописывает
настоящий адрес в **конец** списка — то есть первым остаётся то, что прислал сам
отправитель. Любой смог бы выдать себя за сеть ЮKassa.

Сейчас связка такая и правится только парой:

- `server/Caddyfile.precettore` → `header_up X-Real-IP {remote_host}` —
  перезаписывает заголовок настоящим адресом соединения;
- `api/generate-hw.js` → `clientIp()` читает только `x-real-ip` (и
  `x-vercel-forwarded-for`, пока жив откат), а запасной вариант — адрес сокета.

Проверено живьём: запрос с подставленным `X-Real-IP: 6.6.6.6` и с
`X-Forwarded-For: 185.71.76.1` возвращает настоящий адрес соединения, а
поддельный вебхук ЮKassa получает 403.

> **Проверено 12.08.2026 — адрес клиента виден настоящий.** Проверять после
> переключения DNS не пришлось: сервер опрошен снаружи по временному имени
> (`check.precettore.ru` с `tls internal` в `precettore.caddy` плюс
> `curl --resolve …:201.24.127.48`, блок сразу снят). `/api/healthz` вернул
> `ip` = внешний адрес машины, а не `172.x` — то есть NAT докера адрес не
> подменяет и проверка вебхука ЮKassa цела. Способ годится и для любой
> будущей проверки сервера до переключения домена: Let's Encrypt на боевое имя
> заранее не выпустить, а `tls internal` эту проблему обходит.
>
> Прежняя формулировка (оставлена как способ перепроверки после DNS):
> ```bash
> curl -s https://precettore.ru/api/healthz
> ```
> Поле `ip` должно совпасть с вашим внешним адресом (`curl -s ifconfig.me`).
> Если там окажется адрес вида `172.x.x.x` — проверка вебхука ЮKassa сломана, и
> её надо чинить до приёма платежей.

## Разворачивание с нуля

Один раз на сервере (всё уже сделано 12.08.2026, здесь — для воспроизводимости):

```bash
# пользователь для деплоя; в группу docker НЕ добавляем
useradd -m -s /bin/bash deploy
install -d -m 700 -o deploy -g deploy /home/deploy/.ssh
# в /home/deploy/.ssh/authorized_keys — открытый ключ из секретов GitHub

install -d -m 755 /opt/precettore-web
install -d -m 755 -o deploy -g deploy /opt/precettore-web/current
install -m 600 -o root -g root /dev/null /opt/precettore-web/api.env

# право ровно на одну команду вместо членства в группе docker: утёкший секрет
# репозитория не должен означать root на сервере с базой
echo 'deploy ALL=(root) NOPASSWD: /usr/bin/docker restart precettore-web' \
  > /etc/sudoers.d/precettore-deploy
chmod 440 /etc/sudoers.d/precettore-deploy && visudo -c
```

Контейнер и конфиг:

```bash
scp server/docker-compose.web.yml precettore-db:/opt/precettore-db/
ssh precettore-db 'cd /opt/precettore-db && sh run.sh config add web'
scp server/Caddyfile.precettore \
  precettore-db:/opt/precettore-db/volumes/proxy/caddy/precettore.caddy
# в конец основного Caddyfile — одна строка:
#   import /etc/caddy/precettore.caddy
ssh precettore-db 'cd /opt/precettore-db && docker compose up -d web caddy'
```

Секреты — `/opt/precettore-web/api.env` по образцу
[`server/api.env.example`](../server/api.env.example). Ключи базы берутся из
`/opt/precettore-db/.env` (`ANON_KEY`, `SERVICE_ROLE_KEY`) — копировать их
откуда-то ещё не надо.

**Правка `api.env` требует `docker compose up -d web`, а не `restart`**:
`restart` не перечитывает `env_file`.

## Автодеплой

`.github/workflows/deploy.yml`: push в `main` → сборка на раннере → `rsync` →
`sudo docker restart precettore-web` → проверка `/api/healthz`.

Секреты репозитория: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`,
`DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`.
Переменные: `DEPLOY_ENABLED=1` включает задачу, `HEALTH_URL` — если проверяться
надо не по боевому адресу.

Ключи ЮKassa, токен бота и `service_role` в CI **не кладутся**: они нужны только
на сервере, а секрет, которого нет в CI, из CI не утечёт.

Отпечаток сервера закреплён в `DEPLOY_KNOWN_HOSTS`
(`ssh-keyscan -t ed25519 <ip>`), `StrictHostKeyChecking` включён — иначе первый
коннект доверял бы любому, кто ответит по адресу.

Раскатка идёт `rsync --delete` прямо в `current/`, без атомарной подмены
каталога. Так сделано сознательно: Caddy держит `current/dist` примонтированным,
и подмена каталога по симлинку заставила бы пересоздавать ещё и Caddy, то есть
ронять заодно прокси базы. Цена — пара секунд неконсистентности при раскатке.

В бандл едет прод-набор `node_modules` целиком (~160 МБ) из того же
`package-lock.json`, что и у клиента. Отдельного `package.json` для сервера нет
намеренно: разъехавшиеся версии `@supabase/supabase-js` на клиенте и на
сервере — ровно тот баг, который потом не находится. При желании набор можно
ужать до одного `@supabase/supabase-js` — это единственная внешняя зависимость
`api/`.

## Порядок переключения домена

Пока не сделано — DNS ещё смотрит на Vercel (`216.198.79.1`). Сервер:
`201.24.127.48`.

1. **Заполнить оставшиеся секреты** в `/opt/precettore-web/api.env`:
   `DEEPSEEK_API_KEY` и `TELEGRAM_BOT_TOKEN` (из @BotFather). Из Vercel их не
   вытащить: переменные помечены Encrypted и обратно не читаются.
2. **Перевыпустить секреты бота.** `TELEGRAM_WEBHOOK_SECRET` — любое новое
   случайное значение. `TELEGRAM_DB_SECRET` — новое значение плюс его SHA-256 в
   базу (`supabase/telegram_bot_rpc.sql`). После этого бот на Vercel перестанет
   работать — то есть делать это надо непосредственно перед переключением.
3. `docker compose up -d web` — перечитать env.
4. **Поменять A-запись** `precettore.ru` в панели reg.ru на `201.24.127.48`.
   TTL желательно снизить заранее.
5. **Включить боевой блок** в `precettore.caddy` (раскомментировать
   `precettore.ru { import precettore_site }`) и перечитать конфиг:
   ```bash
   docker exec supabase-caddy caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile
   ```
   Именно в таком порядке: включённый заранее блок не прошёл бы проверку
   Let's Encrypt (она уходила бы на Vercel), а Caddy уводит неудачные попытки в
   экспоненциальную паузу — сайт мог бы пролежать ещё до часа после переключения.
6. **Проверить**: вход репетитора и ученика, realtime доски (`wss://`), адрес
   клиента в `/api/healthz`, ответ бота, генерацию ДЗ.
7. Только после этого — удалить проект на Vercel и `vercel.json` из репозитория.

## Откат

Пока проект на Vercel жив, откат — это возврат A-записи на `216.198.79.1`.
Код на Vercel продолжает собираться с каждым push в `main`, поэтому откат
возвращает актуальную версию, а не стухшую. Единственное, что откатом не
чинится, — перевыпущенные на шаге 2 секреты бота: их пришлось бы вернуть в
переменные Vercel вручную.
